## 1. 可行性判断

技术上可行，附件的主路线合理：冻结有限参数实例的生成 RTL，作为行为参照；再将 Python 的类型推导、FU 选择、拓扑连接等生成规则写成原生 SystemVerilog 的参数、常量函数和 generate 结构；通过独立测试与对照测试逐步替换。

现有 Python 主要在描述 RTL 和组织硬件实例，因此不涉及把普通软件算法重新设计成硬件。不过，交付一个可长期二次开发的 SV 工程，工作量明显大于导出一份 Verilog。

| 交付范围 | 判断 | 主要工作 |
|---|---|---|
| 附件 G00 固定标量 4×4，独立 SV 仿真和综合 | 可行性高，但原始资产需补齐 | 固定参考 RTL、顶层、真实自检 TB、构建入口 |
| 可维护的参数化单 CGRA | 可行，主要工程投入所在 | 参数和类型合同、各层行为等价、合法参数覆盖 |
| 向量/浮点、三类 Tile、多 CGRA、异构拓扑、DMA 等全范围 | 原理上可迁移；不能根据 G00 推定全部已可用 | 各配置独立取证、外部 IP、复杂状态与网络验证 |
| 正常配置、测试和构建全面脱离项目 Python | 可实现，需要重建软件侧配套 | 测试配置、参考结果、配置入口、构建和报告工具 |
| EDA 工具内部调用 Python | 用户已明确允许 | 记录工具及依赖版本，不再要求环境移除 Python |

未发现必须依赖 PyMTL 才能表达的硬件机制。风险主要在行为保真、验证覆盖和工具依赖，而不是 SystemVerilog 的表达能力。

## 3. 主要难点和对附件的修正

### 3.1 恢复的是生成规则，不是数字替换

附件已正确处理有序 FuList、ready 合并、最后有效 FU 的输出优先级、package 的类型作用域等问题，应保留这些要求。

还需归档每个参考实例实际展开后的 FU 顺序。目标源码 `cgra/CgraTemplateRTL.py` 使用 `set` 去重再构造列表，不能把重新运行所得顺序当然视为原次序。仅用 FU 使能位掩码，也不足以表达所有原有顺序。

参数化应明确合法支持域，包括 1 个端口/节点时的宽度退化、非方形阵列、FU 组合、延迟、存储 bank/depth、异构 Tile 和地址区间。多 CGRA 模板的形状选择及控制器的地址偏移推导已有特定假设；“任何正整数参数都支持”不是目前源码能保证的合同。

### 3.2 周期语义是迁移核心，不能统一规范化

控制步可能跨多个周期。寄存器未写入时的默认 token、写入后的 token 消耗、done 位、常量推进和上下文清除必须逐项保持。向量 FU 还可能多次使用操作数，或读取 msg/val 却不拉高 ready。

附件应修正两处通用表述：

- 第 489 行附近的“有效数据”比较不足以作为所有模块的对照规则。`ac96:noc/LinkOrRTL.py:36–37` 无条件 OR 两路 payload/predicate，即使一路 `val=0`，其数据仍可能影响有效输出。应比较所有定义明确、可能被观察到的位，不能统一按 val 屏蔽整个 msg。
- 第 80 行的“等待期间的数据稳定性”应改成保持各接口实际的等待行为。目标 PyOCN 的 `SwitchUnitRTL.py:35–43` 仲裁使能恒为 1，grant 直接选择输出；等待 ready 期间可能继续轮转。新增“锁住 grant 直到握手”的逻辑会改变基线周期行为。

三类 Tile 的状态更新条件也不完全相同，不能先合并成一个状态机、仅加功能开关，再假定等价。基础 FIFO/RF 的复位、满空边界和同时读写语义同样需要独立核对。

### 3.3 旧版本缺陷与语言迁移必须分开

目标 ac96 中已确认：

- `lib/opt_type.py` 中 `OPT_STREAM_LD` 与 `OPT_GEP` 同为 88。全项目恢复统一操作码定义时，必须保留并限制原有使用条件，或者另行版本化修复；不能无说明地重新编号。
- `AdderRTL` 的 `OPT_SUB_CONST` 没有拉高常量 ready，附件已登记这一问题。使用普通 `OPT_SUB` 的通过记录不覆盖它。
- `ConstQueueDynamicRTL` 依据同一周期 `send_const.rdy & ctrl_proceed` 推进；当前较新代码增加了 `consume_pending`，行为不同。
- 后续提交还修改过 Crossbar prologue、FU 输入 ready、谓词 store 等行为。当前源码的通过结果不能直接作为 ac96 的验证结果。

建议先建立“旧行为/已知缺陷/拟修复行为”清单。先等价迁移再独立修复，或先形成经确认的修正版基线再迁移，两条路线都可行，但不能在迁移中暗中混用。

此前 B/C2 NoC 优化也应独立处理。当前 Crossbar 文件同时包含其他历史修复，不能整文件搬运到 ac96 后沿用旧证明。默认暂不纳入此次基线；如需纳入，应单独适配并重新验证。

### 3.4 未定义信号不能借迁移自动消失

目标源码存在向量临时量只写部分位、子 FU 输入高位未连接、普通/Streaming Tile 的 const clear 未连接等情况。需按实际消费者区分：确定无用位、功能相关未定义位、需要单独修复的缺陷。

不应通过初始化全部为零或把所有 X 都作为 don't-care，使差分测试表面通过。Verilator 主要采用二态语义，其结果本身不能证明四态 X 行为等价；相关模块需要明确的比较掩码、静态检查或适用的四态/形式检查。[Verilator 官方语言说明](https://verilator.org/guide/latest/languages.html)

### 3.5 独立验证需要重新建设

附件现有 G00 记录只覆盖 Tile 0 的简单计算和回读，尚不能证明 16 个 Tile 动态工作或跨 Tile 通信。原 Python sink 多检查输出顺序，也不自动证明逐周期等价。

现有 SV 测试平台不能直接作为完整回归入口：核查发现某些失败仅打印文本、之后正常 `$finish`，部分成功判据不完整。新 TB 应保证错误、超时、缺少/多余输出都使进程失败，并通过故意注入一个错误验证检查器确实能报错。

建议同时保留三类证据：

1. 同一输入和反压序列下的逐周期对照，比较控制握手与所有约定的输出位。
2. 独立期望结果测试，避免参考版和迁移版共同存在的错误被“相互相等”掩盖。
3. 小模块的形式等价/性质检查，以及系统层的覆盖矩阵；不能承诺由一次整机对照证明所有参数组合。

打包/解包测试应使用归档的已知配置字作为独立样本，避免 DUT 与 TB 共享同一个错误的字段定义而同时通过。

### 3.6 工具链可以支撑，但必须先锁定实际路径

本机 Yosys 同时提供支持有限 SV 子集的 `read_verilog -sv` 和 `read_slang`；现有流程也可走 sv2v 转换。不能简单认定“Yosys 不支持 SystemVerilog”，也不能由单文件通过推定 package、类型参数和跨模块数组组合均可用。

在批量改写前，应拿接近最终接口的小型设计，验证 package、parameter type、packed/unpacked 数组、generate、端口结构和内存推导，选定版本和前端。

sv2v 需要将有关文件一起处理以解析 package/类型依赖，并会丢弃 assertions。因此不能把通过 sv2v 后的设计当作原 SV 断言已被执行的证据。[sv2v 官方说明](https://github.com/zachjs/sv2v)

本机 Verilator 的 `sys_lib/tools/oss-cad-suite/share/verilator/include/verilated.mk` 存在用 Python 调 `verilator_includer` 的常见编译路径；官方 5.026 构建模板也有这类调用。用户最新澄清允许工具内部调用 Python，因此这项依赖不再构成迁移障碍，也无需仅为排除 Python 而更换模拟器。仍需记录完整工具依赖并验证实际构建路径。[Verilator 5.026 构建模板](https://github.com/verilator/verilator/blob/v5.026/include/verilated.mk.in)

日常开发的边界是：硬件直接维护为 `.sv`，测试平台使用 SV，项目构建采用 Make/Shell、综合使用 Yosys 脚本；不需要运行 PyMTL 或 Python 生成器来更新硬件。EDA 工具内部的 Python 辅助脚本可以保留。独立性验收应确认脱离原 Python 项目仍能构建、配置和回归，而不是检查机器上是否安装 Python。

以上为静态检查和工具帮助信息核查，本次没有执行该最小工程或独立性试验。

### 3.7 配置工具和外部 IP 不能遗漏

架构解析、编译器/YAML 配置转换、测试向量生成等 Python 软件功能，并不会随 RTL 导出而迁移。SV 参数、配置 package 和已版本化数据可服务已知配置；如果要求继续读取现有 YAML/编译器输出并生成任意新程序，需要明确替代工具和允许使用的实现语言。保存几个固定测试向量不能替代原来的配置能力。

已有 HDL 也需逐项确认可综合性和依赖。核查发现 `DW02_multp.v` 标明为仿真模型，主要行为位于 `translate_off` 中；文件另带专有授权声明。`ALUgenMAC.sv` 文件头也有 Genesis 非商业版本声明。这里仅记录文件事实，不能据“已有 .v/.sv”就认定所有 IP 均可直接作为可综合、可分发的交付物。需确定对应 IP 是否在交付范围，以及授权核心或替代实现。

G00 使用现有组合访问存储配置。若未来要换成同步 SRAM/FPGA BRAM，读延迟、读写冲突和复位语义需单独设计，不应作为无行为变化的语言转换处理。

## 4. 对实施顺序的建议

保留附件 T00–T12 主结构，补充或前移以下工作即可，无需重写整份计划：

1. **T00 补齐真实参考资产。** 先形成可追溯 G00，区分附件历史通过与本机新验证。
2. **正式改写前完成工具小样。** 验证 SV 类型/参数表达、仿真和综合，并确认构建不依赖原 Python 项目，防止大批源码写完再改变接口风格；允许工具内部 Python。
3. **固定实例阶段即建立可靠独立 TB。** 附件的回读 28 可作为启动测试，但应尽早补上所有 Tile 的动态参与、跨 Tile 传输和受控反压，之后再宣称 CGRA 级覆盖。
4. **从基础类型到系统逐层替换。** 每层保存行为参照、独立预期结果、参数支持域与已知差异；复杂 Tile/向量/多 CGRA 分别验收。
5. **配置和测试迁移与 RTL 并行。** 不等 T11 才发现缺少无 Python 的新程序配置入口。
6. **最后做全功能清单关闭与 PPA 测量。** 在同一 G00 参数、库、综合前端和时序估计条件下比较生成参考 RTL 与原生 SV。此次语言迁移不自动继承原 NoC 优化的面积/频率改善目标，也不能复用其不同实例的数值。

建议后续从 ac96 建立独立 `codex/sv-migration` 分支或隔离 worktree，保留当前 NoC 分支。参考资产冻结、基础工程、各模块迁移、测试移植和旧缺陷修复分别提交；每次实验记录命令、版本、结果、失败原因及负责代理。本次没有创建该分支。
