# 固定 4×4 VectorCGRA 的 NoC 优化计划

状态：2026-09-17 已完成本轮计划内实验与验证；总面积下降 37.3787%，整机频率受基线未定义信号限制未能可靠给出，尚不能确认双目标同时达成。过程、偏差、子智能体分工和结果统一记录于 `EXPERIMENT_LOG.md`。以下保留原始计划与当时的准备状态。

## 1. 已确认的边界

- 基于 `cgra/test/CgraRTL_test.py::test_vector_mesh_4x4` 的硬件参数：4×4 Mesh、32-bit payload、现有 FU 组合、6 项控制存储、每寄存器银行 16 个寄存器、2 个数据存储银行、每银行 16 项。具体参数保存在基线 manifest 中。
- 固定硬件实例，不固定运行时程序。原有合法配置流、编码和端口编号保持兼容，不要求重新编译或映射。
- 优化范围包括 Tile 通信所涉及的 crossbar、通道、输出合并和握手逻辑，并分析配置环和访存互连的面积。FU 计算功能和存储容量保持不变。
- 同样的复位、配置、输入和外部背压下，完整 CGRA 对外逐周期 `val`、`rdy`、有效 `msg` 和完成通知保持一致。内部无效消息若会影响其他有效路径，也须保持原语义。
- 不增加延迟、不降低吞吐、不减少队列容量、虚通道、组播等通信能力。
- 在 `sys_lib/` 内组织综合、验证、结果和文档；使用已有 NanGate45 typical 库及统一 Yosys/ABC 流程。
- 不设面积或频率提升的通过门槛。优化后如实记录结果，由用户决定后续操作。功能与周期等价仍是硬约束。

## 3. 初步面积画像与优先级

当前数字来自保留层级的映射诊断，尚待阶段 A 审核工具告警与计量口径后冻结为正式基线。总面积为 **3,272,792.978 Liberty 面积单位**，共 **2,063,725 个映射单元**。

| 部分 | 全 CGRA 面积占比 |
|---|---:|
| 配置控制环 | 54.99% |
| Tile FU | 13.89% |
| Tile 寄存器簇 | 11.39% |
| Tile 控制存储 | 7.04% |
| Tile routing crossbar | 3.84% |
| CGRA controller | 3.14% |
| 数据存储及相关控制 | 2.01% |
| Tile 输入通道与 LinkOr | 1.22% |
| Tile FU crossbar | 1.15% |
| 常量存储 | 0.93% |
| 其他 | 0.39% |

最大具体热点是控制环中的 **51 个 6 选 1、199 位 Mux**，合计约占全 CGRA 面积的 **38.76%**。当前翻译经过 sv2v 后出现动态切片 `in_[(5 - sel) * 199+:199]`。应先检查这种选择逻辑的生成和映射成本，不能把这个占比直接当作可节省的面积。

因此先研究宽 Mux，再研究 Tile crossbar 的 prologue 与译码共享。暂不从增加流水线、减少缓冲、压缩运行时配置能力等方向入手。

## 4. 分阶段执行

### A. 冻结可复现的基线与测量流程

1. 审查已经准备的脚本，固定工具版本、PyMTL fork commit、库 SHA256 和实例参数。
2. 在加载标准单元库定义后重新检查映射网表，区分工具库识别告警、原始 RTL 未驱动信号和实际影响测量的问题，不把 warning-only 的工具退出当作正确性证明。
3. 面积采用完整 CGRA 的分层映射结果，所有存储统一映射到标准单元，输出可加和的模块及单元类型统计。
4. 尝试展平同一份已映射网表，使用随 Yosys 提供的 ABC 对跨模块组合路径估计延迟；统一 BUF_X1 驱动、5 fF 端点负载。检查组合环、未驱动的有效路径和所有单元覆盖情况。
5. 如仍需调整测量实现，先固定新口径，再用同一口径重跑基线和所有候选。

交付：参数与版本清单、脚本、完整面积分解、原始日志索引及测量限制。

时序结果明确标为“综合组合延迟估计”和其倒数对应的频率参考值。它不包含完整 clock-to-Q、setup、时钟树和布线时序，不称为签核 Fmax。若工具无法给出可信结果，记录缺失原因，不用局部延迟代替。

### B. 单独优化控制环的宽 Mux

1. 检查原 Mux 的合法选择、无请求时选择、消息无效周期和越界选择语义。
2. 评估常量索引的显式选择或译码实现，避免把动态切片综合成代价过高的逻辑。
3. 保留仲裁器、仲裁推进条件、端口顺序、信用计数、虚通道、队列深度和寄存器边界。
4. 优先在本仓库内提供可注入的等价组件，避免修改虚拟环境中的 PyMTL 或留下未管理的 PyOCN 子模块改动。
5. 先做 Mux/SwitchUnit 等价验证与局部综合，再接入完整控制环与 CGRA，执行逐周期差分和完整综合。

交付：一个独立、可回退的实现提交，附局部与完整设计的变化数据；收益不预设。

### C. 单独评估 Tile crossbar 的逻辑共享

在阶段 B 有结果后，按测得开销决定是否继续以下候选，逐项实现和统计：

- 提取每个输入是否被输出选中的共享译码，减少 counter 更新条件重复。
- 将 prologue 的 `counter < configured_count` 比较前移，再选择 1-bit 结果，减少多位动态选择。
- 评估输入需求与有效性归约的共享，避免重复生成按输出选择的逻辑。

保留 multicast `send_accepted`、`compute_done` 特例、reset/clear 时机和无效消息置零。原有截断索引行为也需要纳入等价检查，不能顺便修改语义。

交付：每个候选单独提交、验证及面积/延迟统计，不把多项变换混为一次无法归因的修改。

### D. 集成验证与最终对比

- 组件级：组合或时序等价检查，加逐周期差分测试；覆盖错峰接受的多播、背压、prologue 0–7、地址切换、动态配置、reset/clear、START 和 compute_done。
- 集成级：相关 Tile、控制环和 4×4 CGRA 用例；若改变公共接口，覆盖三种 Tile 变体。
- 翻译级：执行 RTLIR→Verilog 验证，并按仓库要求尝试 `--test-verilog`。Windows/Verilator 的工具链限制单独记录，不把 Python 仿真当成导入构建通过。
- 对外行为：用相同输入和外部背压比较逐周期接口，覆盖边界端口、配置加载和完成通知。
- 结果：按相同流程列出基线、B、C 各候选和最终版本的总面积、模块占比、单元数、组合延迟及频率参考值，注明对应 commit 与日志。

## 5. Git 管理方式

计划确认后才执行以下版本管理安排：

1. 从当前基线建立 `codex/noc-4x4-opt` 分支，后续工作在该分支进行。
2. 第一笔提交仅包含审核后的测量脚本、验证基础设施、参数、计划和基线摘要；不混入 RTL 优化。
3. 每项 RTL 优化独立提交，连同对应验证与结果摘要一起记录。例如：控制环 Mux、crossbar counter 条件共享、prologue 选择共享分别成提交。
4. 失败或收益不佳的实验保留明确记录；已经提交的实验通过 `git revert` 回退，保持历史可读。
5. `tools/`、`.venv/`、缓存、巨型生成网表和临时日志继续忽略；将精简 JSON/CSV/Markdown 报告放入可跟踪的 `sys_lib/results/`，记录源码 commit、工具版本和文件 hash。
6. 保留现有 `sys_lib/lib/` 内容。将库纳入提交前，核实来源与许可；也可只提交固定来源、版本、校验值和获取说明。

每阶段报告对应 commit、修改范围、已完成检查、未完成检查和测量结果，便于直接查看 diff 或回到任一阶段。推送、PR 和合并作为后续操作处理。
